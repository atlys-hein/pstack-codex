# Shipping

Read the [Codex execution contract](../../pstack/CODEX.md). Shipping requires authorization for the specific merge or landing scope. Verification does not confer it.

1. Read the authoritative PR chain, current head and base SHAs, merge policy, approvals, and required checks through the GitHub connector or supported CLI fallback. Establish the authorized set and its dependency order. Stop any competing branch writers before landing begins.
2. Verify each PR independently before it lands. Use a native verifier that did not write the code when available and meaningful. Give it the exact base and head, relevant behavioral scenarios, permitted checks, and evidence paths. It inspects the diff and runs the relevant user-facing or public-interface behavior. Report `PASS`, `PASS+NOTES` for non-blocking notes, `FAIL`, or `BLOCKED`. A blocked lane is not a pass. Green CI alone is not behavioral proof.
3. Find the contiguous verified run from the lowest unmerged PR. Stop at the first PR without an acceptable verdict and any required approval. A verified upper PR cannot skip an unverified dependency. Moving it to the main base changes its context and requires authorized topology changes plus a fresh verification decision.
4. Bind every verdict to the verified head, base, and relevant artifacts. Before using an older verdict, compare the effective patch, for example with `git patch-id --stable`, and inspect changes to its base and dependencies. Equal patch IDs alone do not prove equal behavior on a changed base. Preserve a lane only when its exercised code and context remain equivalent and the evidence explains why. Every new head still needs its applicable current checks. Any uncertain context or conflict resolution requires the affected lanes again.
5. For a tests- or docs-only follow-up, an unaffected built-runtime lane may remain valid if build outputs are equivalent apart from identified, demonstrated nondeterminism or embedded SHAs. Compare repeated builds to establish noise. The follow-up still needs review and its own checks. A dev-server lane without comparable artifacts must rerun when equivalence cannot be shown.
6. Land one PR at a time, bottom-up, with the repository's supported merge method. Re-read the head, base, current checks, approvals, and verdict immediately before the action. Prefer a supported expected-head guard. If the tool cannot atomically guard against a concurrent writer, ensure exclusive ownership and report the remaining race rather than pretending it is eliminated.
7. Read the PR back after the merge request. Confirm it is merged into the intended base. A successful command may have only enabled auto-merge or joined a queue. Do not report a merge until the forge confirms it. Auto-merge is allowed only when the user's grant covers it and the verified head cannot silently change under another writer.
8. After a parent lands, move the next child onto the actual merge result only when stack maintenance is authorized. The designated topology owner performs any required rebase, retarget, or protected push; obtain missing destructive-operation authorization rather than assuming a merge request covers it. Recheck the effective patch, context, and CI before the next merge. Never merge a child into an obsolete parent branch by accident.
9. Leave the stack unchanged while a merge is in flight except for the single authorized next-child transition. Use bounded native or forge waits. Persistent monitoring needs the user's scheduling request and a supported automation tool. Stop at the agreed ceiling. Extending it requires a new verification pass and authorization for the added scope.

Reply with the verified run and ceiling, verdict provenance, merges confirmed by the forge, and the first remaining gap.
