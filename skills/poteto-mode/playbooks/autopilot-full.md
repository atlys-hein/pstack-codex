# Autopilot-full

Read the [Codex execution contract](../../pstack/CODEX.md). Use this for independent changes whose requested lifecycle includes building, verifying, and landing. The parent owns acceptance and independent verification. One scoped owner controls each branch.

A verdict covers specified code and context. CI covers a specific head or merge result. A request to write the plan is not permission to execute it, and "full autonomy" does not remove explicit user gates.

1. Establish the queue, dependency graph, acceptance criteria, and actual authorization for commits, pushes, PRs, merges, and any infrastructure cost. Items reserved for the user and items outside the queue stop at the applicable gate. If the changes depend on one another or the user wants to land them, use [Autopilot-stack](autopilot-stack.md).
2. Give each independent item a native owner with an exclusive worktree or non-overlapping resource scope. A separate agent ID is not isolation. Each brief carries the complete current constraints, branch/base identity, acceptance tests, permitted lifecycle actions, and required reports. The parent stays available for decisions and does not launch a second full router inside every worker.
3. Owners implement, run the permitted checks, review their own diffs, and create PRs through [Opening a PR](opening-a-pr.md) only when authorized. Opening early is useful when CI can run on a coherent change, but never publish an unfinished or unrelated diff merely to create activity. Record each code-ready head and every later head. Keep a local decision trail and artifacts in the permitted task area; no hidden agent store or cloud durability is assumed.
4. Check base drift before the first independent verification. Reconcile only when needed for correctness or the planned landing context. Preserve unrelated work and one branch writer. Any protected history rewrite needs the appropriate authorization and a lease based on the observed remote SHA. An unexpected remote push stops the owner from overwriting it.
5. At the code-ready head, the parent assigns independent verification lanes for the actual risks. Include the load-bearing user-visible or public-interface behavior, relevant regression checks, and diff review. Use **swarm** for distinct coverage, bounded by runtime capacity. Every lane receives exact head and base references plus evidence requirements. Audit its actual receipts before declaring the item verified.
6. Consolidate proven findings into one scoped fix round for the owner. Include equivalent sites with the same defect when they belong to the task. A defect that already exists unchanged on the base is reported separately; a defect newly copied or reached by the change belongs to this PR. Preserve one writer. Continue with the owner for stateful fix rounds rather than spawning a concurrent replacement.
7. A major new behavior or redesign needs renewed broad verification. A small fix or necessary rebase reruns the affected lanes at the new head. Apply [Shipping](shipping.md)'s patch-and-context rule to any lane carried forward. Every new head still needs its applicable current CI. A self-reported green summary is insufficient.
8. Before an authorized merge, inspect current base changes. Reconcile conflicts, shared-file changes, dependency changes, and changes to which checks run. For affected callers or dependencies, test the actual proposed merge result in an isolated permitted checkout when needed. Do not rebase reflexively for unrelated base movement. A lockfile exception is justified only by a frozen install on the merge result and evidence that the changed dependencies resolve as intended. Repeated collisions go to the parent for sequencing.
9. The parent releases only the exact verified item to its owner for authorized landing through Shipping. A gate relaxation, such as a higher budget or allowlist entry, needs independent justification and parent review. Neither can bypass a forge-enforced approval or the user's gate. Do not disable or soft-fail checks to obtain green status.
10. Keep a bounded registry of owners, branches, current heads, evidence, pending gates, and last progress. Inspect native agent state and actual outputs after completions and meaningful waits. Before replacing a stuck writer, stop it and establish exclusive ownership. Carry preserved edits and a consolidated brief into its replacement. Persistent audits require an explicit scheduling request and a supported automation tool.
11. On a stop request, stop new assignments and send a no-new-writes instruction to every owner. Reconcile running actions, preserve local state, and use [Pause safely](pause-safely.md). Do not silently leave a merge or automation armed outside the user's stop intent.

Reply with each item's current head and verdict, confirmed merges, unfinished gates, verified PR links, and trail locations. Report meaningful changes during the run without repeating unchanged state.
